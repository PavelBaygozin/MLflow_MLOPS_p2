# ЗАДАНИЕ №1

## Управление данными с использованием DVC

Цель: Организация управления данными и автоматизация ML-пайплайнов с помощью DVC. Настройка удаленного хранилища и интеграция с CI/CD для обеспечения воспроизводимости и автоматизации.

### Инициализация и настройка DVC

1. **Инициализация DVC**:
   ```bash
   dvc init -f 
   ```

2. **Добавление данных в DVC**:
   ```bash
   dvc add data/input/train.csv
   ```

3. **Фиксация изменений в Git**:
   ```bash
   git add data/input/train.csv.dvc .gitignore
   git commit -m "Добавлены исходные данные в DVC"
   ```

### Настройка удаленного хранилища (Yandex Object Storage)

1. **Создание бакета**:
   - Уникальное имя бакета: `mlops-bpa-1`.

2. **Настройка DVC для работы с Yandex Object Storage**:
   - Получите `Access Key ID` и `Secret Access Key`.

3. **Добавление удаленного хранилища**:
   ```bash
   dvc remote add -d storage s3://mlops-bpa-1/data
   ```

4. **Настройка параметров доступа**:
   ```bash
   dvc remote modify storage endpointurl https://storage.yandexcloud.net
   dvc remote modify storage access_key_id <your-access-key-id>
   dvc remote modify storage secret_access_key <your-secret-access-key>
   ```

5. **Проверка конфигурации**:
   ```bash
   dvc remote list
      ```

6. **Синхронизация данных**:
   - Загрузка данных в удаленное хранилище:
     ```bash
     dvc push
     ```
   - Получение данных из удаленного хранилища:
     ```bash
     dvc pull
     ```

## Интеграция с CI/CD (GitHub Actions)

1. **Создание файла CI/CD**:
   - Файл `.github/workflows/dvc-pipeline.yml` автоматизирует процесс обработки данных и синхронизации с удаленным хранилищем.

2. **Настройка секретов в GitHub**:
   - В разделе `Settings → Secrets and variables → Actions` добавьте:
     - `DVC_REMOTE_ACCESS_KEY_ID`: Access Key ID для удаленного хранилища.
     - `DVC_REMOTE_SECRET_ACCESS_KEY`: Secret Access Key для удаленного хранилища.

3. **Логирование в CI/CD**:
   - После каждого запуска пайплайна результаты будут логироваться в GitHub Actions.

## Управление экспериментами с MLflow

Цель: Настройка MLflow для управления экспериментами, их сравнения и документирования результатов.

### Настройка MLflow

1. **Установка MLflow**:
   ```bash
   pip install mlflow
   ```

2. **Запуск MLflow-сервера**:
   ```bash
   mlflow ui
   ```
   Чтобы остановить сервер, нажмите Ctrl+C в терминале, где он запущен.
   После остановки сервер перестанет быть доступным по http://127.0.0.1:5000 

### Проведение экспериментов

1. **Создание файла `train_data.py`**:

2. **Запуск обучения**:
   ```bash
   python src/train_data.py
   ```

### 1. **Accuracy (Точность)**:
   - **n_estimators = 50**: Accuracy = 0.275
   - **n_estimators = 100**: Accuracy = 0.289

   **Вывод**:
   - Модель с `n_estimators = 100` показала немного более высокую точность (0.289) по сравнению с моделью с `n_estimators = 50` (0.275).
   - Разница в точности между двумя моделями составляет около 0.0138, что является незначительным улучшением. Это говорит о том, что увеличение количества деревьев с 50 до 100 не привело к существенному улучшению точности.

### 2. **F1 Score**:
   - **n_estimators = 50**: F1 Score = 0.2557
   - **n_estimators = 100**: F1 Score = 0.2566

   **Вывод**:
   - Обе модели показали очень близкие значения F1 Score: 0.2557 для `n_estimators = 50` и 0.2566 для `n_estimators = 100`.
   - Разница между значениями F1 Score минимальна (около 0.0009), что указывает на то, что увеличение количества деревьев практически не повлияло на баланс между точностью и полнотой.

### 3. **Общие выводы**:
   - **Эффективность гиперпараметра `n_estimators`**:
     - Увеличение количества деревьев с 50 до 100 привело к незначительному улучшению Accuracy (на 0.0138) и практически не повлияло на F1 Score.
     - Это может быть связано с тем, что данные не требуют сложной модели, или с тем, что другие гиперпараметры (например, `max_depth`, `min_samples_split`) могут иметь большее влияние на качество.
   - **Качество модели**:
     - Значения Accuracy и F1 Score для обеих моделей остаются низкими (Accuracy ~0.27–0.29, F1 Score ~0.25–0.26), что указывает на то, что модель плохо справляется с задачей классификации. Это может быть связано с:
       - Недостаточной предобработкой данных.
       - Несбалансированностью классов.
       - Неподходящим алгоритмом для данных.
   - **Оптимизация ресурсов**:
     - Поскольку модель с `n_estimators = 50` показала практически такие же результаты, как и модель с `n_estimators = 100`, использование меньшего количества деревьев более предпочтительно с точки зрения вычислительных ресурсов.
